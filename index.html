    Chapter 01

    JSONって、結局なに？

    ひとことで言うと、「記入済みの申込用紙」です。

    あなたが役所や病院で書く申込用紙を思い出してください。 「氏名」「年齢」「電話番号」という項目名が印刷されていて、その横の空欄にあなたの答えを書きますよね。

    JSONは、それをコンピュータが読める形にしただけのものです。それ以上でも以下でもありません。

    申込用紙を、JSONにすると 
    {
  "氏名": "山田花子",
  "年齢": 34,
  "電話番号": "090-1234-5678"
}

    ↑ 左側（青い文字）が項目名、右側があなたの答え。真ん中の : が「＝」の役割です。これだけです。

    これは「プログラミング」ではありません

    ここが一番大事なところです。JSONには、計算する機能も、条件分岐も、繰り返しもありません。 できるのは「情報を並べて書く」ことだけです。

    料理でたとえるなら、JSONはレシピの材料表であって、調理の手順書ではありません。 「玉ねぎ 2個、豚肉 300g」と並べるだけ。炒めたり煮たりするのは、それを受け取ったAIやアプリの仕事です。

    JSON = JavaScript Object Notation

    名前に「JavaScript」と入っていますが、JavaScriptを知らなくても関係ありません。 生まれた場所がそこだったというだけで、今では言語もツールも問わず、世界中で使われる共通フォーマットです。 読み方は「ジェイソン」。

    なぜ、あなたがこれを学ぶ必要があるのか

    AIエージェントを使いはじめると、次のような場面で必ずJSONと出会います。

    AIツールの設定ファイル

    Claude Code や各種AIツールに「どのサービスと繋ぐか」を教えるファイルが、たいていJSONです。

    MCPの接続設定

    AIにGmailやカレンダーを繋ぐとき、公式サイトからコピペするあの設定がJSONです。

    AIへの出力指示

    「この形式で答えて」とAIに渡す型。指定できると、AIの返事が一気に安定します。

    APIからの返事

    外部サービスがデータを返してくるときの、標準的な包み紙です。

    つまり、JSONが読めない＝AIツールの設定でつまずき続けるということ。 逆に言えば、この教材を読み終えたあなたは、公式ドキュメントのコピペで詰まらなくなります。

    Q. JSONにできないことは、次のうちどれ？

    正解：合計金額を計算する
    JSONは情報を書き並べるだけの入れ物です。計算はできません。日本語もふつうに書けます。

    !ここだけ覚えて

    • JSONは「記入済みの申込用紙」。項目名と答えのペアを並べたもの
    • プログラミングではない。計算も判断もしない
    • AIツールの設定でほぼ必ず出会う

    Chapter 02

    いちばん小さいJSONを読む

    部品はたった4つ。波かっこ、キー、値、そしてコロンとカンマ。

    いきなり長い設定ファイルを見ると圧倒されますが、どんなに巨大なJSONも、この4つの部品の繰り返しでできています。 分解して、ひとつずつ見ていきましょう。

    最小のJSON 
    {
  "name": "Claude"
}

    部品①　波かっこ { } — 用紙そのもの

    一番外側の { と } は、「ここからここまでが1枚の用紙です」という囲いです。 始まりと終わりが必ずペアになります。開いたら、必ず閉じる。

    部品②　キー — 項目名

    "name" の部分。用紙に印刷されている「氏名」にあたります。 キーは必ずダブルクォート " で囲みます。ここは例外なし、絶対のルールです。

    部品③　値 — あなたの答え

    "Claude" の部分。空欄に書き込む中身です。 値には6つの種類があって、それは次の章でやります。

    部品④　コロン : とカンマ ,

    コロンは「＝」。キーと値をつなぎます。
    カンマは「次の項目があります」の合図。項目と項目のあいだに置きます。

    項目が増えたら、あいだにカンマ 
    {
  "name": "Claude",
  "model": "opus",
  "enabled": true
}

    注 最後の "enabled": true の後ろにカンマがないことに注目。「次はもうありません」という意味です。ここは間違えやすいので、第6章でもう一度やります。

    読むときのコツ：インデント（字下げ）を見る

    JSONの行頭のスペースは、コンピュータにとっては意味がありません。人間が読みやすいように下げているだけです。 でも逆に言えば、字下げの深さ＝入れ子の深さ。同じ深さの行は仲間、と覚えると長いファイルが一気に読めるようになります。

    深掘りキーの名前は自由に決めていいの？

    JSONの仕様としては、ダブルクォートで囲まれていれば何でもOKです。日本語も、記号も、スペース入りも通ります。

    ただし実務では自由ではありません。設定ファイルのキー名は、そのツールが決めた名前をそのまま使う必要があります。 "mcpServers" と書くべきところを "mcpservers" と書くと動きません。 大文字・小文字も区別されます。

    つまり、設定ファイルを書くときの正解は「公式ドキュメントからコピペする」。自分で打つと必ずtypoします。

    Q. 次のうち、JSONとして正しいのはどれ？

    正解：{ "name": "Claude" }
    キーは必ずダブルクォートで囲みます。1つ目はクォートなし、3つ目はシングルクォート（'）なので、どちらもエラーになります。

    !ここだけ覚えて

    • { } は用紙の囲い。開いたら必ず閉じる
    • キーは必ずダブルクォートで囲む
    • : は「＝」、, は「次があります」の合図
    • 最後の項目の後ろにカンマは付けない

    Chapter 03

    値に書けるのは、6種類だけ

    覚えることは、この表がすべてです。7つ目はありません。

    「＝」の右側、つまり答えの欄に書けるものは6種類に限られています。 多いように見えますが、実際によく使うのは上から4つです。

    種類書き方どんなとき
    文字列 "こんにちは" 名前、URL、パス、メッセージ。迷ったらこれ
    数値 34 / -1.5 個数、金額、温度。計算に使う数
    真偽値 true / false オン／オフ。「有効にする？」への答え
    null null 「値なし」。空欄のまま提出、の意味
    配列 ["A", "B"] 複数を並べる。買い物リスト（第4章）
    オブジェクト { "k": "v" } 用紙の中の用紙。入れ子（第5章）

    いちばん大事な区別：クォートが付くか、付かないか

    非エンジニアがつまずくポイントの第1位がここです。ルールはシンプルで、 文字列だけがクォートで囲まれ、それ以外は裸で書きます。

    正しい書き分け 
    {
  "userName": "花子",
  "age": 34,
  "isActive": true,
  "nickname": null
}

    ↑ 「花子」だけがクォート付き。34・true・null は裸です。

    意味が変わってしまう例 
    {
  "age": ⟦"34"⟧,
  "isActive": ⟦"true"⟧
}

    ⚠ これはエラーにはなりません。JSONとしては正しい。でも意味が変わります。 "34" は「数の34」ではなく「3と4という文字」、"true" は「オン」ではなく「trueという4文字」。 受け取ったツールが「数値を期待していたのに文字が来た」と怒る、気づきにくいタイプの不具合です。

    true / false / null は、小文字で裸のまま

    この3つはすべて小文字で書きます。True（先頭大文字）や TRUE（全部大文字）はエラーです。 Excelや他の言語に慣れている人ほど間違えるので、意識して小文字にしてください。

    「null」と「空文字」と「項目がない」は、全部ちがう

    "nickname": null ＝ 項目はあるが、値は無いと明示
    "nickname": "" ＝ 項目があり、値は「空っぽの文字列」
    項目ごと書かない ＝ そもそも質問されていない

    受け取る側のツールは、この3つを別物として扱います。公式ドキュメントに書かれている通りに合わせるのが安全です。

    深掘り文字列の中でクォートや改行を使いたいときは

    文字列はダブルクォートで囲むので、中にダブルクォートを入れたいときに困ります。 そのときは直前にバックスラッシュ \ を置いて「これは囲いじゃなく文字です」と伝えます。これをエスケープと呼びます。

    エスケープの例 
    {
  "quote": "彼は\"すごい\"と言った",
  "path": "C:\\Users\\hanako",
  "memo": "1行目\n2行目"
}

    よく使うのは3つだけ。\"＝ダブルクォート、\\＝バックスラッシュ本体、\n＝改行。
    特にWindowsのファイルパスは \ を2つ重ねる必要があるので、設定ファイルでよく事故ります。

    Q. 「通知をオフにする」設定として正しいのは？

    正解："notify": false
    真偽値は小文字・クォートなし。1つ目はエラーにはなりませんが「falseという文字列」として扱われ、意図通り動かないことがあります。2つ目は大文字始まりなのでエラーです。

    !ここだけ覚えて

    • 値は6種類：文字列・数値・真偽値・null・配列・オブジェクト
    • クォートが付くのは文字列だけ。数値・true/false・null は裸
    • true / false / null はすべて小文字
    • "34" と 34 は別物。エラーは出ないが意味が変わる

    Chapter 04

    { } と [ ] の使い分け

    カルテか、買い物リストか。この2つを見分けられれば、JSONは半分読めたも同然です。

    JSONに出てくるかっこは2種類。見た目は似ていますが、役割はまったく違います。 ここを混同するのが、つまずきポイントの第2位です。

    { } 波かっこ ＝ カルテ

    項目名で引くもの。
    「氏名は？」「年齢は？」と名前を指定して中身を取り出します。順番に意味はありません。

    [ ] 角かっこ ＝ 買い物リスト

    番号で引くもの。
    ただ並んでいるだけで、名前は付いていません。順番に意味があります。

    見分け方は「中にキーがあるか」だけ

    { } の中は「キー: 値」のペア 
    {
  "name": "山田花子",
  "age": 34
}
    [ ] の中は値だけがカンマ区切りで並ぶ 
    ["りんご", "みかん", "ぶどう"]

    ↑ キーがありません。「りんご」に名前は付いておらず、ただ1番目にあるだけです。

    実際には、この2つを組み合わせて使います

    現実の設定ファイルでいちばん多いのが、「カルテを何枚も束ねたリスト」という形です。 社員名簿を想像してください。1人ぶんの情報がカルテ（{ }）で、それが人数ぶん並ぶ（[ ]）。

    members.json — いちばんよく見る形 
    {
  "members": [
    { "name": "山田花子", "role": "編集" },
    { "name": "佐藤太郎", "role": "デザイン" }
  ]
}

    ↑ 外側は用紙（{）、"members" の答えがリスト（[）、リストの中身が1人ぶんのカルテ（{）。 字下げの深さを見れば、どこが何なのかが見えてきます。

    閉じかっこが並ぶ理由

    長いJSONの末尾で } ] } のように閉じかっこが連続して不安になりますが、これは開いた順の逆に閉じているだけです。 カルテを閉じて、リストを閉じて、いちばん外の用紙を閉じる。心配なら、開きかっこと閉じかっこを上下で見比べて、字下げの位置が揃っているかを確認してください。揃っていれば正しく閉じられています。

    深掘り空っぽのときはどう書く？

    中身がなくても、かっこは書きます。 [] は「リストはあるが空」、{} は「用紙はあるが記入なし」。 設定ファイルで "mcpServers": {} と書いてあったら、「接続先を入れる場所は用意したが、まだ何も入れていない」という意味です。

    ここを null や空欄にすると、ツールによっては動かなくなります。空でも、かっこは残す。

    Q. 「好きな色を3つ挙げる」項目に使うべきなのは？

    正解：[ ] 角かっこ
    同じ種類のものが複数並ぶときはリスト。"colors": ["赤", "青", "緑"] と書きます。

    !ここだけ覚えて

    • { } ＝ カルテ。名前で引く。中は「キー: 値」
    • [ ] ＝ リスト。順番に並ぶ。中は値だけ
    • 実務でいちばん多いのは「カルテを束ねたリスト」
    • 中身が空でも、かっこは書く（[] / {}）

    Chapter 05

    入れ子 — 箱の中の箱

    長いJSONが読めない理由は、難しいからではなく、入れ子が深いからです。

    申込用紙の「住所」欄が、実は「郵便番号・都道府県・市区町村」の小さな用紙になっていることがありますよね。 JSONでも同じことができます。値の場所に、もう一枚の用紙を丸ごと入れる。これが入れ子です。

    住所を入れ子にする 
    {
  "name": "山田花子",
  "address": {
    "zip": "150-0001",
    "pref": "東京都",
    "city": "渋谷区"
  }
}

    ↑ "address" の答えが、文字列ではなく用紙まるごとになっています。これだけのことです。

    深い入れ子を読むコツは、たった1つ

    字下げの位置が同じ行だけを、縦に拾って読む。 これで、何十行あっても構造がつかめます。

    上の例なら、いちばん浅い階層は "name" と "address" の2つだけ。 つまり「この用紙の項目は2つ」とわかります。zip や pref は、address の中の話なのでいったん無視していいのです。

    読み方の手順

    1. いちばん外側の { を見つける
    2. その1段だけ内側にあるキーを、上から拾う（これが「大項目」）
    3. 関係ある大項目を1つ選び、その中だけを同じやり方で読む

    実物を読んでみる

    AIツールの設定ファイルは、たいていこの形です。怖がらずに、上の手順で分解してみてください。

    よくあるAIツールの設定ファイル 
    {
  "theme": "dark",
  "editor": {
    "fontSize": 14,
    "wordWrap": true
  },
  "shortcuts": [
    { "key": "cmd+k", "action": "search" },
    { "key": "cmd+s", "action": "save" }
  ]
}

    ↑ 大項目は theme / editor / shortcuts の3つだけ。 theme は文字列、editor は用紙、shortcuts はカルテのリスト。 17行が、3行の話に縮みました。

    深掘り「エディタの文字サイズ」の場所を人に伝えるには

    上の例で 14 という値の場所を説明したいとき、こう書きます。

    パス表記 
    editor.fontSize

    外側から内側へ、キーを . でつないだもの。これをパスと呼びます。 リストの中を指すときは番号を使い、shortcuts[0].key のように書きます。 番号は0から始まるので、1番目が [0]、2番目が [1] です。

    公式ドキュメントやエラーメッセージにこの表記が出てきたら、「外側からたどれ」という道案内だと思ってください。

    Q. 上の設定ファイルの「大項目」はいくつ？

    正解：3つ
    theme / editor / shortcuts。内側の fontSize などは、大項目の中の話なので数えません。

    !ここだけ覚えて

    • 値の場所には、用紙（{ }）やリスト（[ ]）を丸ごと入れられる
    • 読むときは同じ字下げの行だけを縦に拾う
    • 内側は後回しでいい。まず大項目の数を数える

    Chapter 06

    エラーの9割は、この7つ

    ここが本書の核心です。JSONで詰まる原因は、ほぼこの7パターンに集約されます。

    JSONは融通がききません。たった1文字違うだけで、丸ごと読めなくなります。 裏を返せば、原因のパターンは決まっているということ。順番に潰していきましょう。

    やらかし 1／7
    最後の項目にカンマを付けてしまう

    圧倒的第1位。項目を1つ消したときに、カンマだけ残るのが典型的なパターンです。

    エラーになる 
    {
  "name": "Claude",
  "model": "opus"⟦,⟧
}

    ✕ カンマは「次があります」の合図。次が無いのに付けると、JSONは「約束が違う」と怒ります。閉じかっこの直前にカンマがあったら、それは間違い。

    やらかし 2／7
    項目のあいだのカンマを忘れる

    1つ目の逆です。項目を足したときに起こります。

    エラーになる 
    {
  "name": "Claude"⟦ ⟧
  "model": "opus"
}

    ✕ "Claude" の後ろにカンマが必要です。「最後の行以外は、すべてカンマで終わる」と覚えると両方いっぺんに防げます。

    やらかし 3／7
    シングルクォートを使う

    エラーになる 
    {
  ⟦'name'⟧: ⟦'Claude'⟧
}

    ✕ JSONで使えるのはダブルクォート " だけです。他のプログラミング言語ではシングルでも通るため、ネットで拾ったコードをそのまま貼ると起きがちです。

    やらかし 4／7
    コメントを書いてしまう

    エラーになる 
    {
  ⟦// 使うモデル⟧
  "model": "opus"
}

    ✕ JSONにコメント機能はありません。// も /* */ も # も、すべてエラーです。 メモを残したいときは、下のようにふつうの項目として書いてしまうのが定番の回避策です。

    メモを残したいときの定番 
    {
  "_memo": "opusは高性能だが応答が遅い",
  "model": "opus"
}

    やらかし 5／7
    全角の記号が混ざる

    日本語環境で最も厄介な罠です。見た目がほとんど同じなのに、コンピュータには別物です。

    正しい（半角）間違い（全角）備考
    "” “Wordやメモアプリが勝手に変換する
    ,， 、日本語入力のまま打つと起きる
    :：同上
    { }｛ ｝同上
    （半角スペース）（全角スペース）目で見て気づけない。最凶

    対策：JSONは「日本語入力オフ」で打つ

    値として日本語を書くときだけ入力をオンにする。これだけで全角混入はほぼ防げます。 そもそもWordやメモ帳ではなく、テキストエディタで編集してください。 Wordはダブルクォートを勝手に ” に変えてしまいます。

    やらかし 6／7
    かっこの数が合わない

    コピペで一部だけ持ってきたときや、項目を消したときに起きます。 エラーメッセージが「ファイルの末尾」を指すことが多く、本当の原因はもっと手前にあるのが厄介な点です。

    対処法はシンプルで、字下げを揃え直すこと。揃えてみて形が崩れる場所が、かっこの過不足がある場所です。

    やらかし 7／7
    ファイルの外に文字を書く

    エラーになる 
    ⟦以下が設定です⟧
{
  "model": "opus"
}

    ✕ JSONファイルの中身は、いちばん外側の { で始まり、対応する } で終わるのが原則。その外に説明文があってはいけません。 AIに「JSONを出して」と頼んだときの返事をコピペする際、前後の説明文まで一緒に貼ってしまう事故が非常に多いです。

    Q. 設定ファイルから項目を1つ消したらエラーになった。まず疑うべきは？

    正解：カンマが余っている／足りない
    項目を消すと、その行のカンマだけが残るか、直前の行のカンマが不要になります。削除したあたりのカンマを必ず確認してください。

    !ここだけ覚えて

    • 最後の行以外は、すべてカンマで終わる（1位・2位を同時に防げる）
    • クォートはダブル " のみ。コメントは書けない
    • 全角の ” ， ： と全角スペースに注意。日本語入力はオフで打つ
    • JSONの外に説明文を置かない

    Chapter 07

    エラーメッセージの読み方

    英語で赤い文字が出ても、見る場所は2つだけです。

    JSONのエラーメッセージは英語で、しかも素っ気ない。でも安心してください。 読むべきは「どこで」と「何を期待していたか」の2点だけで、あとは飾りです。

    典型的なエラーメッセージ 
    Expected ',' or '}' after property value
in JSON at position 42 (line 3 column 18)

    ① どこで — line / column

    line 3 column 18 ＝ 3行目の18文字目。
    エディタの行番号を見て、その付近を確認します。

    ② 何を期待していたか — Expected

    Expected ',' or '}' ＝ 「カンマか閉じかっこが来るはずだった」。
    つまりカンマ忘れです。

    よく出るメッセージの日本語訳

    英語意味と、まず疑うこと
    Expected ',' or '}' 項目のあいだのカンマ忘れ（やらかし2）
    Expected double-quoted property name キーが期待された場所に無い。末尾の余分なカンマか、キーのクォート忘れ（やらかし1・3）
    Unexpected token そこにあってはいけない文字がある。全角記号・コメント・シングルクォート（やらかし3・4・5）
    Unexpected end of JSON input 途中で終わっている。閉じかっこが足りない（やらかし6）
    Unexpected non-whitespace character after JSON JSONの外側に余計な文字がある（やらかし7）

    大原則：エラー位置の「少し手前」を見る

    JSONは上から順に読まれ、「おかしい」と気づいた場所でエラーを出します。 でも本当の原因は、たいていその1〜2行前にあります。カンマ忘れなら、忘れたのは前の行だからです。 指された行だけを睨まず、手前の行から見直してください。

    深掘りAIにエラーを丸投げするときの頼み方

    自分で直すのが早いですが、詰まったらAIに聞くのが確実です。そのときこの3点をセットで渡すと、一発で直ります。

    1. JSONの全文（一部だけ切り取らない。原因が切り取った外にあることが多い）
    2. エラーメッセージの全文
    3. 「修正後のJSONだけを、説明なしで出力して」という指示

    3つ目が重要です。これを言わないと説明文が付いてきて、そのままコピペしてやらかし7を踏みます。

    !ここだけ覚えて

    • 見るのは line / column と Expected の後ろだけ
    • 原因は指された場所の1〜2行手前にあることが多い
    • AIに聞くときは「全文＋エラー全文＋説明なしで出力して」

    Chapter 08

    実物を読んでみる

    ここまでの知識で、AIツールの設定ファイルはもう読めます。試してみましょう。

    AIエージェントに外部サービスを繋ぐとき、公式サイトからJSONをコピペする場面があります。 その典型例が、次のような形です。一見こわいですが、分解すれば第5章でやったことと同じです。

    AIエージェントの接続設定（典型例） 
    {
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/hanako/Documents"]
    }
  }
}

    手順どおりに分解する

    1. いちばん外の { がある。これが用紙全体。
    2. 1段内側のキーは "mcpServers" ひとつだけ。つまりこの用紙の項目は1つ。
    3. その中を見ると、キーは "filesystem" ひとつ。これはあなたが好きに付けた接続の名前です。
    4. さらに中に "command" と "args" の2つ。これが実際の設定です。

    "command" は「何のプログラムを起動するか」、 "args" は「そのプログラムに渡す言葉のリスト」。 args が [ ] なのは、渡す言葉が複数あり、しかも順番に意味があるからです（第4章）。

    あなたが書き換えていい場所は、どこ？

    "filesystem" のような自分で付けた名前と、 "/Users/hanako/Documents" のような自分の環境の値だけです。
    "mcpServers" "command" "args" はツールが決めた名前なので、1文字も変えてはいけません。

    接続を2つに増やすとどうなるか

    「カルテを増やす」だけです。そして、あいだにカンマが要ります。

    2つめを追加した状態 
    {
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/hanako/Documents"]
    },
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"]
    }
  }
}

    ↑ 1つめの } の後ろにカンマが付いたのがポイント。「次があります」の合図です。 逆に、あとで github を消すときはこのカンマも一緒に消すのを忘れないでください（やらかし1）。

    深掘りWindowsのパスを書くときの落とし穴

    Windowsのフォルダパスをそのまま貼ると、ほぼ確実に壊れます。 \ がエスケープ記号として解釈されてしまうためです（第3章の深掘り）。

    壊れる
    { "path": "C:⟦\⟧Users⟦\⟧hanako" }
    正しい — 2つ重ねる
    { "path": "C:\\Users\\hanako" }

    多くのツールでは /（スラッシュ）でも動くので、迷ったら C:/Users/hanako と書くのが安全です。

    Q. 上の設定で、あなたが自由に名前を決めていいのはどれ？

    正解："filesystem"
    これは接続に付けたラベルなので、自分でわかりやすい名前にできます。"mcpServers" と "command" はツールが決めた名前で、変更すると動きません。

    !ここだけ覚えて

    • 実物も、分解すれば「用紙の中の用紙」でしかない
    • ツールが決めたキー名は1文字も変えない。コピペが正解
    • 項目を足す・消すときは、カンマもセットで足す・消す

    Chapter 09

    自分で書いて、確かめる

    最後のステップ。書いたら必ず検算する習慣をつけましょう。

    JSONを書くときの鉄則は、いきなり全部書かないこと。 骨組みを作ってから中身を埋めると、かっこの数もカンマも狂いません。

    1. 外側の { } を先に書く。この時点で1回、下のチェッカーに通す
    2. キーを1つだけ足して、また通す
    3. 値を埋めて、また通す
    4. 以降、1項目足すごとに通す

    面倒に見えますが、これが最速です。まとめて書いてから直すと、どこで壊れたかわからなくなります。

    ここで試してください

    下の欄にJSONを貼って「チェックする」を押すと、その場で判定します。 この教材のページ内だけで動き、入力内容がどこかに送られることはありません。

    判定が通ったら、整形（字下げの揃え直し）もできます。字下げが崩れているファイルは、これで一気に読みやすくなります。

    AIに書かせるときのコツ

    自分で1文字ずつ打つより、AIに書かせたほうが速くて正確です。ただし頼み方にコツがあります。

    「〜という設定のJSONを作って。コードブロックの中にJSONだけを出力し、説明は書かないで」

    こう指定すると、そのままコピペできる状態で返ってきます。そして貼る前に、必ず上のチェッカーに通してください。AIも末尾カンマを間違えます。

    !ここだけ覚えて

    • 骨組みから作り、1項目足すごとに検算する
    • AIに書かせるときは「JSONだけ出力して」と明示する
    • AIの出力も、貼る前に必ずチェックする

    Chapter 10

    チートシート

    困ったときは、ここだけ見れば戻ってこられます。

    全部入りの見本 
    {
  "文字列": "クォートで囲む",
  "数値": 34,
  "小数": -1.5,
  "真偽値": true,
  "値なし": null,
  "リスト": ["A", "B", "C"],
  "入れ子": {
    "中の項目": "用紙の中に用紙"
  },
  "最後の項目": "この後ろにカンマは付けない"
}

    チェックリスト

    書く前に

    ・日本語入力はオフ
    ・Wordではなくテキストエディタで
    ・公式ドキュメントからコピペする

    書いた後に

    ・最後の行以外はカンマで終わっているか
    ・閉じかっこの直前にカンマが無いか
    ・クォートはすべて半角ダブルか
    ・チェッカーに通したか

    迷ったときの早見表

    こう思ったら答え
    クォートは付ける？文字列だけ付ける。数値・true/false・null は裸
    { } と [ ] どっち？名前で引くなら { }、順番に並べるなら [ ]
    カンマはどこに？項目と項目のあいだ。最後には付けない
    メモを書きたいコメントは不可。"_memo" のような項目にする
    中身が空のとき{} や [] と書く。消さない
    Windowsのパス\\ と重ねるか、/ を使う
    エラーが出た指された行の1〜2行手前のカンマを見る

    ✓おつかれさまでした

    • JSONは「記入済みの申込用紙」。プログラミングではない
    • キーはダブルクォート、値は6種類、かっこは2種類
    • エラーの9割はカンマ・クォート・全角文字
    • 書いたら必ず検算する
    チェッカーに戻る 最初に戻る
